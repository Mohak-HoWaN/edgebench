# Phase 5: Raspberry Pi agent and multi-device experiments

**Goal:** the same experiment runs on the PC and on the Pi, with thermal and throttle tracking, and results from both appear side by
side.

## Decided (owner, 2026-11-09)
- Developer tool: the owner opens the EdgeBench website in the **Pi's browser**. The "This device" panel (Phase 3) recognises a Pi and
  shows the install command; the agent is installed once by hand on a **development Pi** and then updates itself from the EdgeBench
  server. The fleet agent is not involved. The shop's production Pi is out of scope.
- The Pi has its own internet (Wi-Fi, LAN or hotspot). Support two network modes and test both: same network (direct address) and
  different networks (Tailscale or a tunnel; the agent only makes outbound calls). Record the choice per device. The Pi's browser must
  reach the server's web port too; on the same network that is the PC's LAN address with a firewall rule for the port.

## Decide first (Plan agent + ADR)
- Agent update mechanism and token rotation; what the server does if the Pi's clock is wrong (no RTC) so timestamps in results stay
  trustworthy (use server receive time plus the agent's monotonic offsets).
- Overlay choice for mode (b) and how the server address and token are embedded in the install command.

## Build
- `edgebench-agent` for ARM64 Raspberry Pi OS: **no PyTorch, no Ultralytics**. Runtimes only (onnxruntime, openvino if the wheel
  exists, ncnn). `pip install edgebench-agent` from a local wheel served by the EdgeBench server, then
  `edgebench-agent enroll --server http://<pc>:<port> --token <token>`. The Devices page shows the generated copy-paste command.
- Auth: per-device token generated by the server, stored hashed, revocable; LAN binding of the server is switched on here with
  rate limiting. Tokens never appear in logs.
- Pi telemetry: `vcgencmd measure_temp`, `measure_clock arm`, `get_throttled` (decode under-voltage, frequency-capped, throttled,
  soft temperature limit, and the "has occurred" bits), CPU governor, per-core load. Sampled in a separate process. There is no power or
  energy measurement (owner decision: no power meter).
- Core pinning with `taskset`; threads via each runtime's own setting (ORT `intra_op_num_threads`, OpenVINO `INFERENCE_NUM_THREADS`,
  ncnn `opt.num_threads`). Governor change to `performance` only with explicit permission in the UI and restored afterwards.
- Dataset and artifact transfer: resumable download, sha256 check, cache by hash so each is sent once.
- Multi-device experiments: one wizard run fans out per device; the experiment page shows progress per device, current variant, live latency
  and temperature charts, streaming logs, pause / cancel / resume. (The separate Live run page was removed on 2026-11-12: it only repeated
  the progress bars. A live view comes back inside the experiment page once there are charts to show, Phase 6.) A device going offline marks its runs `lost` and does not stop the
  others.
- Device-specific builds: TensorRT engines are built by the **PC agent** (RTX 4050) as a job, not by the server.
- Cooling notes: user-entered text per device, stored in the manifest.

## Acceptance
- A fake-ARM test: the agent runs on the PC in a "Pi profile" with the `vcgencmd` calls replaced by a fixture, covering throttle bit
  decoding and invalid-for-latency marking.
- Real (needs the Pi; if it is not reachable say "not checked"): enroll, run ONNX FP32 and OpenVINO INT8 on the 10-image fixture,
  see temperature rise during the run, a heat-induced throttle flags the run invalid. Kill Wi-Fi mid-run: the run is `lost`, the agent
  reconnects, nothing duplicates.
- The Pi's measured FP32 vs INT8 ordering is compared with the PC's and the difference is explained in the UI notes.

## Skills
`architecture`, `Plan` agent, `security-review` (tokens, download endpoint, LAN exposure), `diagnosing-bugs`, `simplify`,
`code-review`, `run`.

## Risks
Wheel availability for ARM64 (from Phase 0). Pi 5 under-voltage from a weak supply invalidates results; the throttle bits show it.

## From Phase 0 (binding; see `docs/phase-0-verdict.md`)
- Pi requirements, from the package index (not tested on a Pi): 64-bit OS, glibc 2.35 or newer (OpenVINO), Python 3.11 or newer
  (ONNX Runtime 1.25). The "This device" panel must say "install 64-bit Raspberry Pi OS" when the browser reports `armv8l`.
- Pin per Python version; the newest numpy/scipy lack Python 3.11 ARM wheels. Repo pins that do have aarch64 wheels: numpy 2.2.6, scipy 1.16.3,
  onnxruntime 1.25.1, openvino 2026.1.0, ncnn 1.0.20261020, pnnx 20261020, opencv-python-headless 4.12.0.88, psutil 7.2.2.
- Measure, do not assume: ncnn is slower than ORT/OpenVINO on x86 here but is designed for ARM; ONNX INT8 behaviour on ARM is unknown.
- Protocol and security: ADR 0003. Network modes (same network, or Tailscale) are still untested.
